STATUS MIGRASI FIREBASE STORAGE -> MINIO
PT Adytia Putra Tehnik - dashboard
Update: 30 Agustus 2026

==============================================================
SELESAI HARI INI
==============================================================

Arsitektur: server Express (server/) di VPS, terpisah dari Firebase
Cloud Functions (project masih Spark plan, Functions v2 + panggilan
keluar ke non-Google host butuh Blaze). Auth tetap verifikasi Firebase
ID Token via firebase-admin. Presigned URL S3 (PUT/GET) ke MinIO.

Prefix yang sudah dimigrasi (baca kode: sudah tidak pakai
firebase/storage sama sekali, semua lewat server/ + secureStorage.js):

1. inventori/     - privat, tulis: admin, baca: presigned (butuh login)
2. pekerjaan/     - privat, tulis: admin, baca: presigned (butuh login)
                    (kode jalan & teruji, tapi menurut user belum dipakai
                    di praktik)
3. nidi_data/     - privat, tulis: admin, baca: presigned, dukung PDF
                    (sertifikat NIDI/SLO)
4. instansi/      - PUBLIK-BACA (bucket policy MinIO, bukan presigned),
                    tulis: editor (admin/superadmin/editor)
5. pengujian/     - PUBLIK-BACA, tulis: owner (uid di path) ATAU admin
                    -> INI YANG MEMPERBAIKI INSIDEN PRODUKSI AKTIF
                    (Firebase Storage quota-exceeded, upload TTD client
                    di PengujianAdminDetail gagal sebelum ini)

Bug nyata yang ikut diperbaiki selagi migrasi pengujian/:
- MobileFormPengujian.jsx: buildSafePhotos/mergePhotos dulu hardcode
  cek `startsWith("https://firebasestorage")` untuk tahu foto sudah
  ke-upload atau belum. Dengan URL MinIO, foto yang SUKSES ke-upload
  akan selalu dianggap "masih pending" selamanya. Diganti jadi
  isRemoteUploadedUrl() - cek "bukan URI lokal" (bukan whitelist 1
  domain), jadi tidak akan rusak lagi kalau provider storage ganti lagi.
- Batas ukuran file foto megger di PekerjaanRLO.jsx (20MB di frontend)
  diselaraskan ke 5MB sesuai storage.rules asli (dulu upload 5-20MB
  lolos validasi frontend tapi gagal di Firebase Storage Rules).

Bug PRE-EXISTING yang ketahuan saat audit, TIDAK terkait migrasi ini,
belum diperbaiki:
- maintenanceGardu/ dan laikOperasi/ dipakai aktif di 4 halaman
  (MobileMaintenanceGardu, MobileMaintenanceGarduList, LaikOperasiEditor,
  LaikOperasiManagement) tapi prefix-nya TIDAK ADA sama sekali di
  storage.rules asli -> kena default-deny -> upload di kedua fitur ini
  kemungkinan besar SUDAH GAGAL dari sebelum sesi ini, tidak berkaitan
  dengan migrasi MinIO.

Catatan desain untuk rekrutmen/ (kalau nanti dikerjakan): endpoint
upload sekarang (`getSecureUploadUrl` pola) mensyaratkan login (Firebase
ID Token). Form lamaran kerja (FormLamaran.jsx) upload TANPA login sama
sekali - butuh jalur terpisah yang tidak wajib auth, dengan validasi
lebih ketat (rate-limit per-IP, ukuran file, content-type) untuk
menggantikan proteksi yang tadinya dari Firebase Storage Rules.

==============================================================
DATA LAMA (FOTO/FILE) - BELUM DIMIGRASI
==============================================================

Untuk prefix yang KODE-nya sudah pindah ke MinIO (nidi_data/, instansi/,
pengujian/), file-file LAMA yang sudah ter-upload SEBELUM migrasi ini
MASIH ada di Firebase Storage, dan dokumen Firestore-nya MASIH simpan
URL Firebase lama (https://firebasestorage.googleapis.com/...). Ini
sengaja dibuat begitu (fallback), record lama tetap tampil normal
selama Firebase Storage belum dihapus/kena masalah kuota lagi.

inventori/ dan pekerjaan/ TIDAK punya data lama (sudah dicek awal
migrasi, folder-nya kosong di Firebase Storage) - jadi 2 prefix itu
sudah 100% lepas dari Firebase, tidak ada sisa.

Lihat file terpisah untuk cara memindahkan data lama ini kalau mau
benar-benar lepas dari Firebase Storage sepenuhnya (bukan cuma upload
baru saja yang ke MinIO).
